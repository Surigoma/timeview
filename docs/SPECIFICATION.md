## 目的と利用シーン

上映イベント、カンファレンス、講演で、オペレーターが残り時間とカンペを管理する。演台には表示専用画面を配置し、別PC・同一PCの操作画面、USBテンキー、HTTP対応の外部機器から制御する。上映中は表示専用画面を暗転できる。

会場内LANだけで動作し、通常運用ではインターネット接続を必要としない。サーバーはWindows・macOS・Linuxで動作し、操作・表示はブラウザで行う。1つのサーバープロセスが1つのタイマーを管理し、複数の操作端末・演台端末は同じ状態を共有する。

## システム構成

```text
USB Keypad／MIDI → React操作画面 ─┐
UIなしリモコン（各OS） ──────────┼─ HTTP JSON API → Go（タイマーはメモリ、設定はJSON）
React画面／外部機器・制御ソフト ─┘                    │
                                               └─ SSE → 操作画面／演台画面
```

| 要素 | 採用案 | 役割 |
| --- | --- | --- |
| サーバー | Go + Gin | ルーティング、ミドルウェア、JSON応答、静的ファイル配信、状態配信 |
| UI | React + TypeScript + Vite | 操作画面・演台画面。CSSでレイアウト |
| 状態管理 | Goの構造体・map・sync.Mutex | タイマー状態と再送抑止情報をメモリ内で一括更新 |
| 設定保存 | Koanf + UTF-8 JSONファイル | 設定、定型文、Keypad・MIDI割り当てをDBなしで保存 |
| 入力検証 | go-playground/validator | 設定ファイルとKeypad・MIDI割り当ての宣言的な検証 |
| 流量制限 | golang.org/x/time/rate | APIクライアント単位のトークンバケット制御 |
| 配信 | Server-Sent Events（SSE） | サーバーからブラウザへ最新状態を配信 |
| 配布 | Go embed | 本番はNode.js不要。ビルド時のみフロント用ツールが必要 |
| タスクランナー | Task（go-task） | 開発・検証・ビルド・配布用コマンドをTaskfile.ymlに集約 |

単一プロセスで開始する。SQLite、Redis、メッセージブローカーは導入しない。HTTPの定型処理はGin、JSON設定の変換はKoanf、構造体検証はvalidator、流量制限はx/time/rateへ任せる。タイマーの状態遷移、同時実行制御、再送抑止、設定ファイルの原子的置換は製品固有の処理として実装する。サーバーはOS専用APIへ依存させずCGOなしでビルドする。UIなしリモコンの常駐入力だけはgohookとgomidi/rtmididrvを通して各OSの入力APIを利用し、CGOを有効にして各対象OS上でビルドする。依存バージョンは`go.mod`と`go.sum`で固定する。

画面操作も外部操作も同一のコマンド処理を通す。状態の検証・変更・再送抑止記録を同じロック内で行い、成功後に応答・配信する。通信処理はロック外で行う。DB用の抽象層や移行機構は用意しない。

## 分離ネットワークでの接続

- インターネットから分離された会場内LANで運用する。既定では到達できる端末がすべてのAPIと操作画面を利用できる。ブラウザ操作限定を有効にすると、外部HTTPクライアントは参照APIだけを利用できる。同一オリジンの操作画面からは別端末でも変更できる。
- 認証、ログイン、APIキー、トークン、セッションCookie、役割別の権限管理は設けない。ブラウザ操作限定は要求ヘッダーによる誤操作防止で、端末の本人性は検証しない。
- 通信はHTTPを使用する。TLS終端、証明書の発行・更新、HTTPSへのリダイレクトは不要。
- 操作URLは `http://<サーバーIP>:8080/`、演台URLは `http://<サーバーIP>:8080/display`。表示URLは固定で、再起動後も変更不要。
- 既定待受は `127.0.0.1:8080`。分離LANで利用するときは起動オプションで会場LAN側のIPまたは`0.0.0.0:8080`を指定する。
- React画面とAPIを同じHTTPサーバーから配信する。初回はクロスオリジンのブラウザ連携を対象とせず、CORS許可ヘッダーは付けない。HTTPを直接送る外部機器・ソフトは利用できる。
- 起動時に操作URL・演台URLを案内する。再起動時は画面・外部機器が状態を再取得して接続を復帰する。

## 設定保存とデータの寿命

タイマーの実行状態と通信管理情報はメモリで管理する。DBは使用しない。再利用する設定だけをJSONファイルへ自動保存する。

| データ | 保持内容・寿命 |
| --- | --- |
| 設定・定型文 | 持ち時間、警告、配色、表示モード、表示言語、点滅、ブラウザ操作限定、定型文。JSONへ保存し再起動後も保持 |
| 演台接続・名前 | ページIDごとの応答と名前。応答なし30分・記録削除・サーバー終了で消去。ページ再読込は新ID |
| タイマー | 状態、基準残り時間、単調増加時計の基準点、instanceId、version。サーバー終了まで |
| カンペ | 本文、表示フラグ。サーバー終了まで |
| 暗転 | blackout。サーバー終了まで保持し、次回起動はtrueで初期化 |
| 再送抑止 | 要求キー、要求ハッシュ、結果。10分またはサーバー終了まで |
| Keypad・MIDI割り当て | JSONへ保存し、全操作画面で共有。ブラウザの有効状態は各ブラウザのメモリのみ。UIなしリモコンは`listen`起動時に取得 |

ブラウザの再読み込みや端末の通信断だけでは、サーバー上のタイマーは初期化しない。サーバー再起動時は実行状態だけを初期化し、保存済み設定を復元する。失敗した入力は状態も設定ファイルも変更しない。

レート制限用の追跡情報に期限・件数の上限を設ける。再送抑止・SSEの上限と合わせ、通信要求による無制限のメモリ増加を防ぐ。

操作ログは既定でカレントディレクトリの`timeview-operations.jsonl`へJSON Lines形式で追記し、`-audit-log`で変更できる。起動、正常終了、異常終了と変更操作の操作名、成否、HTTPステータス、エラーコード、操作元を記録する。カンペ本文、設定値、要求本文、毎秒の状態配信は記録しない。各行は追記後に同期し、異常終了直前までの記録を優先する。ログローテーションは初期範囲外とする。

設定ファイルは既定でカレントディレクトリの`timeview-config.json`とし、`-config`で変更できる。初回起動時に既定値で生成する。書き込みは同じディレクトリの一時ファイルを同期後に置換し、途中までのJSONを残さない。未知フィールド、不正値、未対応バージョンは起動時に拒否し、既定値で黙って上書きしない。

## 性能・運用目標

以下は実装後に測定する受入目標であり、現時点の保証値ではない。

| 項目 | 目標・条件 |
| --- | --- |
| 想定規模 | 単一タイマー、表示・操作あわせて50接続 |
| 操作反映 | 安定した有線LAN・RTT 20ms以下で、操作から演台反映までp95 300ms以内 |
| 表示同期 | 同条件で接続中の複数表示間の差が通常200ms以内 |
| 長時間動作 | 8時間連続運用で停止や継続的なメモリ増加がない |
| 時間精度 | スリープなし・正常時刻のPCで1時間の経過誤差1秒以内を目標 |
| ネット接続 | 外部CDN、外部フォント、クラウドAPIを通常動作の必須条件にしない |
| サーバー対象 | Windows・macOS・Linux。配布対象OS／CPUは下記を参照 |
| ブラウザ検証 | Windows: Chrome／Edge、macOS: Safari／Chrome、Linux: Firefox／Chrome。実装時点の安定版で1920×1080と1280×720を確認 |
| アクセシビリティ | 色だけに依存しない状態表示、ラベル、キーボードフォーカス、十分なコントラスト |

GoサーバーPCの電源・スリープ設定と分離LAN内のHTTP接続確認は[運用ガイド](OPERATIONS.md)に従う。

### クロスプラットフォーム配布

| OS | 初期配布対象CPU | 形式 |
| --- | --- | --- |
| Windows | amd64 | `timeview.exe` |
| macOS | amd64、arm64（Apple Silicon） | `timeview` |
| Linux | amd64、arm64 | `timeview` |

各OS／CPU向けにビルドしたサーバー実行ファイルへ同じReact成果物を埋め込み、同じアーカイブへUIなしリモコンを同梱する。利用時にGo、Node.js、SQLiteのインストールは不要。UIなしリモコンはWindowsとmacOSの標準フレームワーク、LinuxデスクトップのX11・ALSAランタイムを利用する。サーバーはCGO無効、UIなしリモコンはCGO有効で、GitHub Actionsの各OSネイティブランナー上でビルドする。パスやシグナル処理をOS依存で固定しない。

各配布対象で起動、終了、API、SSE、初期化動作を検証する。クロスコンパイル成功だけで実行確認済みとは扱わない。対応OSの最低バージョンは、採用するGoとブラウザの動作要件を実装開始時に確認して固定する。インストーラー、自動起動登録、コード署名・公証は初回の範囲外とし、手動起動の配布物として導入手順を記載する。

### Docker配布

DockerイメージはマルチステージでフロントエンドとGoバイナリをビルドし、実行段階は単一バイナリだけを含む `scratch` とする。プロセスは非rootユーザーで実行し、`0.0.0.0:8080`で待ち受ける。設定ファイルと操作ログはコンテナ内の `/data` に置き、このパスへマウントしたボリュームで永続化する。タイマーの実行状態は従来どおり永続化しない。

## 実装順序と成果物

1. Taskfile.ymlとGo／Reactの開発環境を整え、Goのメモリ内タイマー・JSON設定保存・単一タイマーAPIを作り、時間計算と再送抑止を検証する。
2. Reactの操作画面と演台画面、SSE同期、カンペ、画面暗転を実装する。
3. Keypad割り当て、外部API連携例を仕上げる。
4. 再接続・再起動・性能・OS別の試験を行い、Windows・macOS・Linux向け配布物と操作手順を整える。

成果物は、Go／Reactソース、Taskfile.yml、OS／CPU別の実行ファイル、JSON設定ファイル、OpenAPI形式のAPI定義、API操作例、セットアップ・再起動手順、受入試験結果とする。

### Taskによる開発・ビルド

リポジトリ直下に`Taskfile.yml`を配置し、スキーマは`version: '3'`を使用する。Taskの定義形式は[公式ガイド](https://taskfile.dev/docs/guide)に従う。Task本体のバージョンは実装開始時に固定し、開発手順に記載する。

| コマンド | 役割 |
| --- | --- |
| `task --list` | 利用可能なタスクと説明を表示 |
| `task setup` | Go依存とフロント依存をロックファイルに従って取得 |
| `task dev:backend` | 開発用Goサーバーを起動 |
| `task dev:frontend` | Vite開発サーバーを起動。API・SSEはGoへプロキシ |
| `task dev:remote -- <引数>` | UIなしリモコンをソースから実行 |
| `task fmt` | Go・フロントのコードを整形 |
| `task lint` | Goの静的検査、TypeScriptの型検査、フロントのlint |
| `task test` | Go・フロントの自動テストを実行して終了 |
| `task build` | Reactをビルドして埋め込み、実行中のOS／CPU向けGo実行ファイルを生成 |
| `task release` | Reactをビルド後、実行中のOS／CPU向け実行ファイルを生成。全5対象はGitHub Actionsでネイティブビルド |

開発時は別ターミナルで`task dev:backend`と`task dev:frontend`を実行する。Go embedの対象が必要な場合は、バックエンド起動前にフロント成果物を準備する。実行ファイルの出力先は`dist/<os>-<arch>/`とする。

Taskの`dir`・`env`等で作業ディレクトリとビルド環境変数を指定し、Windows専用コマンドやUnix専用の外部コマンドへの依存を避ける。フロントのビルド完了後にGoをビルドする順序を保証し、途中の失敗は非ゼロ終了として伝える。Windows・macOS・Linuxで同じタスク名を使用する。

開発・ビルド環境にはGo、Node.jsとパッケージマネージャー、Taskを用意する。依存取得は開発環境で事前に行い、上映会場では配布済み実行ファイルだけで動作させる。会場での実行にTaskのインストールは不要。

受入時は各開発OSで`task lint`・`task test`・`task build`を確認し、GitHub Actionsが指定した5種類の実行ファイルを各OSのネイティブ環境で生成することを確認する。各成果物の実行確認は[クロスプラットフォーム配布](#クロスプラットフォーム配布)に従う。

## 運用条件と変更時の影響

機器・運用を変更する場合は、次の前提と影響を確認する。未検証の機器は実機で確認する。

| 項目 | 本案の前提 | 変更による影響 |
| --- | --- | --- |
| Keypad実機 | 標準USBテンキー | 専用HID・シリアル機器なら別途接続方式が必要 |
| 操作の常駐性 | ブラウザのKeypadは前面のみ、常時制御はUIなしリモコンの`listen` | OS別の入力監視権限・実機確認が必要 |
| 設置 | Windows・macOS・LinuxのPC・オフラインの分離LAN | 会場のアドレス構成に合わせてHTTP待受先を指定 |
| 時間切れ | マイナス表示で継続 | 0固定や自動停止を希望する場合は状態・表示仕様を変更 |
| 状態の寿命 | 設定はJSONへ保存。実行状態はメモリのみ | 実行中タイマーの復元が必要な場合は別途設計 |
| UI言語 | 日本語／英語 | 設定画面で切り替え、JSONへ保存して全画面へ同期 |
| デザイン | 暗色・大きな時間表示 | 色、ロゴ、レイアウトは画面実装時に調整 |
